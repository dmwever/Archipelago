# 03: "Location does not exist: 3616"

**Reported:** 2026-10-19, playtesting

**Status:** ready-for-agent

## Report

The game reports location 3616 does not exist.

## Audit (from code, not verified in game)

3616 is the **Loom** tech location (`items/Items.py:514`, `TECH_LOOM = 3616`; `TechData.xs:14`).

A tech location is only registered in a scenario when the tech is *not* already researched at
start. `initTech` (`Techsanity.xs:~178-193`) returns early when `xsGetTechState` is
`cTechStateDone` (or `cTechStateInvalid`), and only otherwise calls `AddLocation(itemId)`.

`MarkServerLocations` (`AP.xs:~362-385`) then reads the server's checked-locations file and calls
`SetServerLocationComplete` on every id below `MIN_SCENARIO_ID` (101) — all tech, building, unit
and age ids — without checking whether this scenario registered it. For a location the scenario
never added, `GetLocationById` prints `Location Not Found: 3616` (`ScenarioLocations.xs:25`) and
`SetServerLocationComplete` prints `Location does not exist: 3616` (`ScenarioLocations.xs:132`).

Likely trigger: Loom was checked earlier (another scenario), and this scenario opens with Loom
already researched, so 3616 was never registered here.

Probably cosmetic: the location is already checked on the server, so nothing is lost. But the
same path will print for **any** checked global location the current scenario didn't register —
other already-researched techs, techs the civ can't research, building/unit locations not present
here — so it should grow as more locations are checked.

## To confirm

- Whether Loom had been checked before entering it
- Whether other ids also print, or only 3616

## Agent Brief

> *This was generated by AI during triage.* Approved 2026-10-22 after grilling.

**Category:** bug
**Summary:** `MarkServerLocations` should skip checked global locations the current scenario never registered, without chat output

**Current behavior:**
When the client reports checked locations, `MarkServerLocations` calls `SetServerLocationComplete`
for every global id (scenario part `id / 100` below `MIN_SCENARIO_ID`) and for this scenario's own
objective ids. A global tech location the scenario never registered (granted at start, or out of the
civ's reach), such as Loom (3616) in a Feudal-start scenario after another scenario checked it,
prints `Location Not Found: 3616` and `SetServerLocationComplete: Location does not exist: 3616`.
This repeats on every checked-locations update.

**Desired behavior:**
- A checked global id that is a registered location is marked server-complete, as today.
- A checked global id that is not registered is skipped with no chat output.
- A checked id for this scenario's objectives that is not registered still prints, as today.
- All other lookups (`AP_Check_Location`, `SetScenarioLocationComplete`, `IsScenarioLocationComplete`,
  `SetServerLocationComplete`, `IsServerLocationComplete`) keep printing on an unknown id.

**Key interfaces:**
- New `vector FindLocationById(int id)` in the location ledger: scans the ledger and returns the
  location, or `cInvalidVector`, printing nothing (including for `id == -1`).
- `GetLocationById(int id)`: keeps its `No Id Set` and `Location Not Found` chat lines and finds the
  location through `FindLocationById`. Same signature and return contract as today.
- `rule MarkServerLocations`: the global branch uses `FindLocationById` and sets `serverComplete` on
  the result when found. The branch for this scenario's ids keeps calling `SetServerLocationComplete`.
  Each reported id costs one ledger scan, as today.

**Acceptance criteria:**
- [ ] `FindLocationById` exists, prints nothing, and is the only ledger scan loop;
      `GetLocationById` is built on it.
- [ ] In `MarkServerLocations`, an unregistered global id produces no chat output and is skipped.
- [ ] A registered global id still ends up with `serverComplete` true.
- [ ] An unregistered id for this scenario's objectives still prints
      `SetServerLocationComplete: Location does not exist`.
- [ ] `xs-check` passes on the XS folder (run it with `-I . --`, or it only prints usage).
- [ ] Manual (maintainer, in game): a Feudal-start scenario under `existing_techs` with Loom already
      checked on the server prints nothing for 3616.

**Out of scope:**
- Changing which techs, buildings, units or ages get registered.
- Making `AP_Check_Location` or the other `Set*/Is*` helpers quiet.
- A tech that reads `cTechStateInvalid` at init but becomes researchable later (it would hit a loud
  `AP_Check_Location` and lose the check); not believed to happen, not addressed here.
- Any apworld (Python) change.

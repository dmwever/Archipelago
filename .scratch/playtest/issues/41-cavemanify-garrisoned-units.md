# 41: Cavemanify pulls a garrisoned unit out, and its replacement can be stuck

[#35](35-unit-id-lookup-spike.md)'s follow-up

**Status:** needs-triage

**Blocked by:** none

**Related:** [#10](10-caveman-sweep-delayed.md), [#35](35-unit-id-lookup-spike.md) (all measurements)

## Problem

`transformUnit` (`Caveman.xs:184-198`) replaces a unit by reading its position, calling
`xsRemoveUnit`, then `xsCreateUnit` at that position. A garrisoned unit is listed by
`xsGetPlayerUnitIds`, so cavemanify reaches it. #35 measured what happens:

- Removing a garrisoned unit takes it out of its container on the same tick.
- The position read while it is inside is the container's centre, so the replacement is created
  there, outside the container.
- From a Castle, the replacement stood stuck in the footprint for 23 s despite a move order. From a
  Ram, it walked off.

This happens whatever the rule's timing, which is why it is not part of #10.

## What #35 found

- **A garrison order** (`xsTaskUnits(…, cActionTypeGarrison, …)`) puts the replacement back on the
  same tick for a Town Center, Watch Tower, Donjon, Castle, Siege Tower, Transport Ship and Ram. It
  is refused by a Barracks, Archery Range, Stable, Monastery and Dock.
- **`xsSetUnitProperty(created, cUnitGarrisonedInId, container)`** puts the replacement in on the
  same tick for every container tested, including all five that refuse an order. The force argument
  made no visible difference.
- Ungarrisoning releases every replacement alive, **except from a Dock**: the galleys stayed inside.

## Proposed fix (from #35)

`transformUnit` reads `xsGetGarrisonedInUnitId(unit)` before removing it. If the result is 0 or
above, it puts the replacement into that container with
`xsSetUnitProperty(created, cUnitGarrisonedInId, container)` on the same tick.

## Open before it is ready

- **Dock:** a replacement galley doesn't come out on ungarrison. Is that a Dock-only release rule,
  a different order, or a bug in forcing a ship in?
- **Full container:** not run. The old unit's slot is freed on the same tick, so the replacement
  should fit, and force may matter here.
- **`evictProfession`:** it replaces units the same way and has the same bug for a villager in a
  Town Center. The maintainer ruled eviction out of #10. Whether this ticket covers it is undecided.

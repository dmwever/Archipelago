# 55: Standing buildings do not bring their techs into logic

**Reported:** 2026-10-29, playtesting

**Status:** done

**Related:** [#53](53-granted-units-need-access.md) (the same shape, for units)

## Report

A building already standing at the start of a scenario does not put its techs in logic. In game
you walk up to it and research; logic asks for the building item first.

## Audit (verified by building the world, not only by reading)

> *This was generated by AI during triage.*

### The mismatch

Two rules exist for "this scenario has this building", and they disagree about standing:

| rule | includes `starts_with_building`? |
| --- | --- |
| `ScenarioLogic.has_building` (`ScenarioHasBuilding.answer`) | **yes** - `starts_with_building \| can_build` |
| `ScenarioLogic.has_building_structurally` | **yes** - `starts_with_building \| can_build_structurally` |
| `Logic.can_build_structurally_anywhere` | **no** - `Or(is_unlocked & can_build_structurally)` |

A tech location sits inside its building's region, and `TechRules.set_rules` gates the door into
that region with the third one:

```python
for door in self.doors:
    building = NAME_TO_BUILDING[door.connected_region.name]
    self.world.set_rule(door, self.logic.can_build_structurally_anywhere(building))
```

`can_build_structurally` resolves to `ScenarioCanBuild`, whose answer is:

```python
rule = (buildings.has_building_item(self.building)
        & self._has_builders(scenario)
        & scenario.ages.has_reached(self.building.age))
```

So the door asks for **the building item, builders and the age** - and never asks whether one is
already standing. The scenario-level tech rule knows better: `can_pay_for(tech)` uses
`has_building`, which does count a standing building. The door shuts the player out before that
rule is ever consulted.

### Confirmed against a built world

With `techsanity: all` and all three campaigns, **40 cases** across 10 scenarios have a building
standing while the Can Build door still demands its item. A sample:

| scenario | building standing | door still asks |
| --- | --- | --- |
| The Maid of Orleans | Blacksmith | Blacksmith item |
| The Maid of Orleans | Market, Mill, Stable, Dock, Archery Range, Barracks, Town Center | each one's item |
| The Horde Rides West | Monastery, Market, Mill, Mining Camp, Archery Range, Town Center | each one's item |
| Pax Mongolica | Castle, Stable, Archery Range, Town Center | each one's item |
| Into China | Siege Workshop | Siege Workshop item |
| A Life of Revenge | Barracks, Town Center | each one's item |
| The Rising | Lumber Camp, Mill | each one's item |

No scenario has a standing building it could *never* put up, so no tech is permanently
unreachable by this. The effect is that the techs are gated behind an item the player does not
need, which tightens the fill rather than stranding a seed - the same direction as #51's A2-3 and
G1-1 gates before they were corrected.

The builders half matters too: `_has_builders` is what #51-era work added for the Builder
profession. A fixed-force scenario has no villagers, so a standing Blacksmith there is doubly
shut out.

## What this needs

1. A `has_building_structurally_anywhere` on `Logic`, matching the existing
   `can_build_structurally_anywhere` but folding in `starts_with_building`, and used for the
   Can Build doors.
2. A decision on whether the door is the right place at all. The door is per-building and global
   across scenarios, while "standing" is per-scenario, so an Or over scenarios of
   `is_unlocked() & has_building_structurally(building)` is the shape that matches
   `_can_research`'s own Or.
3. A test. `test_never_bare.py` is the nearest neighbour; the assertion is that for every
   scenario and building, a standing building satisfies the door without the building item.

Note this is the mirror of [#53](53-granted-units-need-access.md): there, logic grants access the
game withholds; here, logic withholds access the game grants. Worth reading together, but they
are not the same fix.

## Agent Brief

**Category:** bug
**Summary:** A building standing at a scenario's start opens its techs and its unit training
without the building item; the build door becomes paid.

**Current behavior:**
Each building with tech or unit locations has a region (named after the building item) that is
reachable only through one exit of the `Can Build` region. That exit's rule is
`Logic.can_build_structurally_anywhere(building)`: an Or over scenarios of
`is_unlocked() & buildings.can_build_structurally(building)`, which asks for the building item,
builders, the age reached, the prerequisite and water access. It never asks whether the building
already stands, and it never asks for payment. So:

- A standing building's techs and units are shut behind an item the player doesn't need (40 cases
  across 10 scenarios with all three campaigns).
- An unpaid but buildable building opens the door, and only the location rules behind it ask for
  payment.

These door rules are set by the tech rules and skipped when `techsanity: none`. In that case
the train doors (`UnitEntranceKind.train`, which reuse the same helper) are the only gate on
training.

**Desired behavior:**
Each building region has exactly two ways in, one for each way of having the building:

- From a new ruleless region **`Starts With Building`** off the origin region: an Or over
  scenarios of `scenario.is_unlocked() & scenario.starting_state.starts_with_building[building]`.
- From **`Can Build`** (unchanged otherwise): the paid `Logic.can_build_anywhere(building)`, the
  same rule as the `Build <building>` location.

Both kinds of door are set whatever techsanity is, by the building rules (the rule set that
already sets `Build <building>`), not by the tech rules.

Train doors leave a building region, so they ask nothing further: the `UnitEntranceKind.train`
entrance rule is `True_()`.

Removals:

- `Logic.can_build_structurally_anywhere` and its cached `_can_build` dict. The one caller left,
  LocalStart's House check (whether this seed can put a House up, unpaid on purpose), gets the Or
  inline.
- The never-bare test's door exemption (`paid_where_they_lead` and its filter). Nothing is left to
  exempt: Can Build doors are paid, standing doors ask no structural question, and train doors are
  `True_()`.
- The stale "Plan 3 will gate Can Build -> Mill" comment in the tech-pool tests.

Unchanged: the `Build <building>` and Age locations stay in `Can Build` with their rules, the tech
and unit location rules (still per scenario and paid), and the ruleless
`<building> to <host> Techs` entrances.

**Key interfaces:**

- `Logic.can_build_structurally_anywhere`: deleted.
- `Logic.can_build_anywhere(building)`: now also the Can Build door rule.
- A new region `"Starts With Building"`, created beside `"Can Build"`, whose exits connect to the
  same building regions.
- `UnitRules.entrance_rule`: the `train` kind returns `True_()`.
- `ScenarioLogic.starting_state.starts_with_building[building]`: the standing fact the new doors
  read.

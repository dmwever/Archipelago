# 45: The caveman ledger is scanned linearly, and it is most of what a full pass costs

**Reported:** 2026-10-28, from [#10](10-caveman-sweep-delayed.md)'s run E

**Status:** wontfix (deferred 2026-10-28 until the lag is felt in play)

**Related:** [#33](33-unitsanity-sweep-cost-spike.md) (measured the ledger scan),
[#35](35-unit-id-lookup-spike.md) (measured the array costs that decide the fix),
[#10](10-caveman-sweep-delayed.md) (put this out of scope and left the measurement behind)

## Report

`originalTypeOf(unitId)` finds a unit's **original unit** by walking the caveman ledger from the
start (`cavemanListIndexOf`, `Caveman.xs:81-89`). The ledger holds up to
`CAVEMAN_LEDGER_CAPACITY` (400) entries. `ApplyCaveman` calls it once for every unit it is given.

#10's redesign made that cheap on a normal tick, because only units that are new to P1 are given
to `ApplyCaveman` — about two a tick. It did nothing for the **full pass**, which still hands it
every unit P1 owns.

## Evidence

Two independent runs, two harnesses, one answer.

| Source | Measurement |
| --- | --- |
| #10 run E, full pass at 205 units, empty ledger | ~46 ms |
| #10 run E, the same at a ~150-entry ledger | ~75 ms |
| **Difference — the ledger scan** | **~29 ms** |
| #33, `ApplyCaveman` alone at 200 units, ledger 0 | ~20 ms |
| #33, the same at ledger 200 | ~50 ms |
| **Difference** | **~30 ms** |

#33 also measured ledger 400 at ~126-139 ms per call, put the scan at ~85% of a full-ledger
call, and costed one ledger comparison at about 2 µs. Its verdict line says an O(1)
`originalTypeOf` "would bring a full-ledger sweep down to about the ledger-0 figure, ~20 ms".

A full pass runs whenever an item arrives or a research finishes, and it is one tick. At run E's
rate that is a stall of two to four frames.

## Also in scope, and cheaper to fix

**`removeDeadCavemen` is quadratic** (`Caveman.xs:125-134`). It walks the ledger, and for each
dead entry calls `releaseCaveman(id)`, which walks the ledger **again** to find an index the
caller already has as `i`. At 400 entries with many dead that is up to 160,000 comparisons.
Passing the index would make it linear, with no index structure and no design decision. It runs
at most every `CAVEMAN_REAP_SECONDS` (2) since #10, so it is a 2 s spike rather than a per-tick
cost, but it is close to free to fix.

`rememberOriginalType` (`:98`) and `releaseCaveman` (`:113`) both open with the same linear scan,
so whatever replaces it serves all four callers.

## What the fix has to decide

#35 measured the facts that choose the shape, and they are in its *Answer*:

- **Unit ids only rise, with no fixed top.** Projectiles use about one id per arrow and corpses
  about one per death; an idle map uses 1 to 1.5 ids a game second.
- **Large int arrays are affordable.** Resizing 1 → 200k every tick did not move the tick rate,
  nor did 200 reads of a 200k array. Arrays were created up to 4M ints.

So an id-indexed array is probably affordable, but it is unbounded in principle and #35 never
pinned the highest id a long scenario reaches. A hash table is bounded but is more code. The
ticket should pick one and say why.

## Out of scope

- Changing `CAVEMAN_LEDGER_CAPACITY`, or what happens when the ledger fills.
- Which units are caveman-exempt, and what `cavemanTarget` picks. Settled in #01 and #16.
- The other two candidates #10's run E raised: `anyUnitWithLockedProfession`'s cost on a full
  pass (~11 ms, inferred from a residual and never measured), and sharding the full pass across
  ticks. Both are separate, and both are worth less than this one.
- Any apworld change. This is game-side only.

What triage established, so returning is cheap:

- **The report is confirmed by code path.** `originalTypeOf` (`:90`) walks the ledger via
  `cavemanListIndexOf` (`:81`); `ApplyCaveman` calls it once per given unit (`:229`);
  `rememberOriginalType` (`:99`) and `releaseCaveman` (`:114`) open with the same scan;
  `removeDeadCavemen` (`:132`) hands `releaseCaveman` an id and makes it re-find the `i` the
  caller already holds.
- **The ticket understates the cost.** `transformUnit` scans two or three times per transformed
  unit: `:191` remembers `CAVEMAN_REMOVED`, and `:198` releases a freshly created id that is
  almost never in the ledger — and a *miss* always costs the full ledger length. #10 run E's
  ~29 ms measured `originalTypeOf` alone, so a sweep that actually transforms units is worse
  than the figure in *Evidence*.
- **A sibling scan, unmeasured.** `isUnitCavemanImmune` (`:50`) is linear, runs in the same
  per-unit loop (`:225`), and — unlike the ledger — sheds entries only when it hits its 256 cap
  (`reapImmuneUnits`, `:22`, is called only from `MarkUnitCavemanImmune` when full). Every
  mercenary soldier ever spawned (`MercenarySpawn.xs:77`) stays on it, so a mercenary-heavy run
  climbs toward 256 and sits there. It did not show up in #10 run E's delta because the immune
  list was constant across both legs. `cavemanExemptTypes` is a different thing — keyed by type,
  capped at 32 — and is not implicated.
- **The design question #45 left open is already answered by #35.** Id-indexed arrays, not a
  hash table: #35 measured 200k-slot resizes every tick as free and created arrays up to 4M
  ints. The shape that makes all four entry points O(1) is *two* id-indexed arrays — id to
  original type, and id to ledger index — with the compact `cavemanUnitIds` list kept only so
  `removeDeadCavemen` has something to walk. The id-to-index array is what lets `releaseCaveman`
  swap with last without searching, and the swap has to rewrite the moved entry's slot.
- **`xsArrayResizeInt(arrayId, newSize)` does not document what it fills grown slots with**, and
  unlike `xsArrayCreateInt` it takes no default. Grow-on-demand must write the `-1` sentinel over
  the new range itself rather than trust the fill — a zero fill would read as `CAVEMAN_REMOVED`
  and make `ApplyCaveman` (`:230`) silently skip every unit above the old high-water mark.
- **Acceptance criterion 4 is a maintainer step.** It needs a live run of `spikes/10/TestE.xs`;
  an agent cannot check it.

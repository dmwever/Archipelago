# 33: Spike: what do the caveman sweep and the unit checks cost per tick?

**Reported:** 2026-10-26, triage of [#10](10-caveman-sweep-delayed.md)

**Type:** spike

**Status:** done

**Blocks:** #10, #34

## Question

How much of the sim tick do `ApplyCaveman` and `checkOwnedUnits` take at high population? Is either
cheap enough to run on every `UnitsanityChecks` tick (once a second)?

Both fixes for #10 rest on this, and nobody has measured it. The early returns in `UnitsanityChecks`
(`Unitsanity.xs:336-347`) are what keep the sweep rare today. The KB warns about exactly this: "A
cheap early `return` in a hot rule masks its true cost"
(`AoE2_AI_Modder/docs/agent/references/XS_MEASURED_BEHAVIOR.md`, *Choosing a poll rate*).

## What the code says (not measured)

- **`ApplyCaveman`** (`Caveman.xs:207`): for each owned unit, `originalTypeOf` scans the caveman
  ledger linearly (up to `CAVEMAN_LEDGER_CAPACITY`, 400). `removeDeadCavemen` walks the ledger once
  per sweep. At 200 pop and a full ledger, that is in the region of 80,000 comparisons.
- **`checkOwnedUnits`** (`Unitsanity.xs:200`): `findUnit` and `canonicalTypeOf` are O(1) array
  reads. #10's brief stopped there and called the function cheap, but it isn't O(1).
  - For every unit whose type has a unit row, `MarkRowOwned` reads `structGetInt(unit, "owned")`
    (`Unitsanity.xs:174`).
  - That read goes through `validateInstanceAttribute` → `findIndexString` (`structs.xs:586,123`),
    a linear string comparison over the Unit struct's attribute names.
  - `MAX_STRUCT_ATTRIBUTES` is 13 and `"owned"` is the 12th, so each read costs about 12 string
    comparisons. There are up to two reads per unit (the type and its canonical type), so a few
    thousand string comparisons per tick at 200 pop.
- **Closest measured evidence** (same KB file, *Per-tick scanning is affordable*):
  - Enumerating the owned-unit id set every tick was within noise.
  - 250 `xsGetObjectCountTotal` calls on every sim tick kept 94% of a 10-second baseline.
  - This suggests `checkOwnedUnits` is cheap, but it is a different workload and doesn't prove it.

## Method

Use the KB's tick-rate method: count rule firings over a 10-second baseline with nothing extra
running, then with the function under test running every tick, and report the retained percentage.

- Put the harness in a throwaway XS file that `.gitignore` covers, never in a live module. Delete it
  once the numbers are recorded.
- Use P1 at about 200 pop of units that have unit rows, under caveman mode, so `ApplyCaveman` does
  real work.
- `ApplyCaveman`: measure with the ledger empty, about 200, and full (400).
- `checkOwnedUnits`: measure at the same population, with rows both owned and not owned.
- Run each at the rule's real cadence (once a second) and at every sim tick, so there is headroom.

## Answer

> *This was generated by AI from three in-game runs on 2026-10-26, all at Fast speed (2.0).*

**Short version:**
- At the rule's real cadence, `checkOwnedUnits` is affordable.
- `ApplyCaveman` is expensive with a full ledger, and the cost is the ledger scan.
- That puts #34 in row 1 of the table and #10 in row 4.
- Run 2 reproduced every per-tick cost from run 1 to within about 10%.
- Run 3, with all 400 units marching across the map, gave the same picture. The full-ledger
  sweep still costs ~140 game-ms per call.

### How it was measured

- **Harness:** a throwaway `Test.xs`, run in `XsTesting.aoe2scenario`. It called the real
  `ApplyCaveman` and `checkOwnedUnits`, with the installed seed's `SlotData.xs` and
  `UnitData.xs`, on 200 P1 units with unit rows. 400 units were on the map, and the ledger
  was built so nothing transformed.
- **Observable:** firings of one `highFrequency` rule per ~10 game seconds, with the work
  inside that rule. A slow tick advances more game time, so the extra game milliseconds per
  firing are what one call costs.
- **Run 1** ran the phases in order, with a baseline at the start and the end.
- **Run 2** ran a baseline before every phase and once at the end. Each phase is read against
  the mean of the baselines either side of it.
- **Results files:** both are kept in `.scratch/playtest/spikes/33/` (`run1.xsdat`,
  `run2.xsdat`, each with its ledger). Both decode with `kit xsdat decode --ledger`: run 1
  passed 125 of 125 checks and run 2 passed 257 of 257. Both footers are present, and no phase
  transformed a unit.
- **Units:** these are game milliseconds. At Fast (2.0), wall-clock cost is half the figure.
  A full-ledger sweep is then ~65–70 ms of real time, about four frames at 60 fps, and
  `checkOwnedUnits` is ~7–9 ms.

### Run 3: every unit on the move

- **Setup:** the same as run 2, except all 400 units spawned in the SW corner and were ordered
  to the NE corner as the first baseline began. They were sent back whenever a baseline step
  started with the lead unit arrived (steps 0 and 14). The file is `run3.xsdat`, and it passed
  278 of 278 ledger checks.
- **The 400-unit move order is a large one-off spike.** Step 0's baseline ran 63.7 ms per
  firing and step 2's 31.2. The return order at step 14 barely registered (18.7). That spike
  sat next to phase 1, so run 3's control reads −13 ms and is void.
- **Settled baselines were faster than runs 1–2:** 16.8–21.4 ms per firing (47–60 firings per
  game second), against 22–30 ms. Most likely the blob left the screen, so less was drawn per
  frame.
  - That points to the firing rate following the render frame rate, which would also explain
    the gap to the kit's 30 turns per game second.
  - It also means the absolute baseline isn't a sim-load meter. Only the differences between
    phases are.
- **Per-call costs hold up under movement.**
  - The full-ledger sweep, alone (140.5) and with the checks (147.2), matches runs 1–2.
  - The smaller workloads read 25–40% lower (caveman ledger 0 and 200, checks). That is
    probably the faster frame giving more slack, not cheaper work.
  - Nothing grew. Movement load did not make either function more expensive.
- **The once-a-second phases are still at the noise floor**, as in runs 1–2.

### Is the method sound?

- **The rate tracks cost.** Phases 2–9 move it by up to 87%, so game time per tick is not
  fixed.
- **The positive control is below the noise.** Phase 1 cost 0.9 and 2.9 ms, against a
  baseline sd of 2.1 ms. That matches the KB's 94% figure, but it is not proof on its own.
  The large phases are what show the meter works.
- **The figures add up.** Phase 9 is within 3–6 ms of phase 4 plus phase 5 in both runs.
- **The noise is scatter, not drift.** Run 2's baselines jump around between 22.4 and
  29.8 ms with no trend, about ±8%. Run 1's "drift" was the same scatter.
  - Anything under ~3 ms per call is unresolvable. That covers the control, the reset, and
    the owned-vs-not-owned difference, which flipped sign between runs.
  - The once-a-second phases sit at the noise floor in both runs: 11 calls spread over 10 s.
    Run 2 even ranked them the wrong way round. Their cost comes from the per-call figures
    instead: 11 × ~130 ms is ~14% of the time for the full-ledger sweep, and 11 × ~16 ms is
    ~2% for the checks.
- **Open question:** the baselines ran 34–45 firings per game second. The kit's verified
  engine fact (`aoe2kit/docs/XS_ENGINE_VERIFIED_2026-09.md`) says 30 turns per game second
  at Fast 2.0. The costs are differences between phases, so they hold either way, but the
  gap is unexplained.

### What the numbers say

- **`ApplyCaveman` scales with the ledger, about 2 µs per ledger comparison.**
  - Per call at 200 units: ~19–20 ms with an empty ledger, ~49–55 ms with 200 entries, and
    ~126–139 ms with 400. With the full ledger recorded first, the average scan is about 300.
  - With a full ledger, the scan is ~85% of the call. A sweep once a second is then a
    ~130 game-ms stall every second, ~14% of game time.
- **`checkOwnedUnits` costs ~14–18 ms per call at 200 units**, roughly 70–80 µs per unit.
  The struct reads dominate.
  - Once a second, that is ~2% of the time, below the noise floor.
  - Every sim tick it would cost ~40% of the tick rate. It must stay on the once-a-second
    rule, never `highFrequency`.
  - Owned and not-owned rows cost the same within noise. A row is unowned only once per game
    anyway.

### Against the table

| Result | Verdict |
| --- | --- |
| `checkOwnedUnits` within noise | **Yes, at once a second** (~2%, below the ~8% scatter). #34 can drop its gate on the existing 1 s rule. Not every sim tick. |
| `ApplyCaveman` within noise even with a full ledger | **No.** A full ledger costs ~126–139 ms per call. |
| `ApplyCaveman` measurable but bounded | Only while the ledger is small: ~20 ms per call empty, ~50 ms with 200 entries. |
| `ApplyCaveman` expensive | **Yes, with a full ledger.** The ledger scan is ~85% of the call. An O(1) `originalTypeOf` would bring a full-ledger sweep down to about the ledger-0 figure, ~20 ms, which is ~2% once a second. |

**Not covered:**
- A mix of unit types; every unit here shared one row. Per-unit cost shouldn't depend on the
  type, because the `"owned"` attribute index is the same for every row.
- Mercenaries in the immune list. `isUnitCavemanImmune` is a second linear scan, up to 256
  entries, and was empty here.

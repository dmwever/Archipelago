# 04: Reach Feudal / Reach Castle sent at the start of Joan 1

**Reported:** 2026-10-19, playtesting

**Status:** ready-for-human

## Report

Reach Feudal Age and Reach Castle Age were sent during Joan of Arc 1 (An Unlikely Messiah). Age
locations should only send when the player completes the research.

## Audit (from code, not verified in game)

XS side, `Ages.xs`:

1. `InitAges` → `ClimbToVanillaAge` forces each age tech up to the scenario's vanilla age to
   `STATE_DONE` (skipped only under `start_in_dark_age`). Joan 1 sets `SetVanillaAge(CASTLE_AGE)`
   (`AP_Joan_1.xs`), so Feudal and Castle are marked done at startup.
2. With `shuffle_ages` on, `InitAges` registers age locations 1–3 and enables `ShuffleAgesUpdate`.
3. `ShuffleAgesUpdate` checks every age whose tech state is `cTechStateDone` — it cannot tell
   "researched by the player" from "granted by the climb", so it fires both on its first tick.

Affects every scenario whose vanilla age is above Dark, not only Joan 1: all Joan scenarios
(Castle start), and Genghis 3–6 / Attila ones starting Feudal or later — whenever
`existing_techs` isn't `start_in_dark_age`.

The apworld already agrees with the report: `ScenarioAgeLogic.can_research`
(`logic/scenarios/ScenarioAgeLogic.py`) only lets an age at or below a scenario's starting age
count when `DARK_START` holds, and `fixed_force` scenarios (Joan 1) can't reach an age at all. So
these are out-of-logic early checks — logic is fine, the game sends too much.

Likely shape of a fix: exclude ages at or below `apVanillaAge` from the shuffle-ages check (or
snapshot which age techs were already done after `ClimbToVanillaAge` and skip those), and decide
whether a `fixed_force` scenario should register age locations at all.

## Agent Brief

**Category:** bug
**Summary:** With `shuffle_ages` on, age locations the scenario starts past are registered and sent on the first tick

**Current behavior:**
With `shuffle_ages` on and `existing_techs` not `start_in_dark_age`, `InitAges` climbs to the
scenario's vanilla age (marking those age techs done) and then registers Reach Feudal, Castle and
Imperial unconditionally. `ShuffleAgesUpdate` checks every age whose tech is done, so in Joan 1
(vanilla Castle) Reach Feudal and Reach Castle are sent at scenario start. Ages above `apMaxAge` are
locked but still registered.

**Desired behavior:**
- An age whose tech is already done after `ClimbToVanillaAge` is not registered.
- An age above `apMaxAge` is not registered.
- Every other age registers and is locked as today.
- `ShuffleAgesUpdate` sends a check only for a done age that was registered. A done age that was not
  registered sends nothing and prints nothing.
- Every done age still counts toward `reached`, so the rule still turns itself off once every age
  up to `apMaxAge` is done.
- The `has_castle` / `has_imperial` unlock order stays as it is today.
- Under `start_in_dark_age` the climb is skipped, so all ages up to `apMaxAge` register as today.

**Key interfaces:**
- `InitAges()` in `Ages.xs`: decides registration per age after `ClimbToVanillaAge` and the
  max-age locks, and records it in one bool per age (module-level, beside `has_castle` and
  `has_imperial`).
- `rule ShuffleAgesUpdate`: reads those bools before calling `AP_Check_Location(age)`.
- No change to `AP_Check_Location`, the location ledger, slot data, the packet or the apworld.

**Acceptance criteria:**
- [x] Joan 1 (vanilla Castle, max Imperial) with `shuffle_ages` on and vanilla-age start registers

- [x] Joan 2 (vanilla Feudal, max Castle) registers only 27 (Reach Castle); researching Castle sends 27.
- [x] A Dark start scenario (e.g. Attila 1) registers all ages up to its max and sends each one only
      when it is researched.
- [x] Under `start_in_dark_age`, every age up to `apMaxAge` registers in every scenario.
- [x] No `Location does not exist` / `Location Not Found` chat from `ShuffleAgesUpdate` in any scenario.
- [x] `ShuffleAgesUpdate` still turns itself off once every age up to `apMaxAge` is done.
- [x] `xs-check` passes on one entry point per campaign, e.g. `./xs-check.exe -I . -- AP_Joan_1.xs`
      (without `-I . --` it only prints usage).
- [ ] Manual (maintainer, in game): Joan 1 with `shuffle_ages` on sends no age checks at start.

**Out of scope:**
- Fixed-force scenarios: no new flag, no special handling.
- `MarkServerLocations` and server-side chat for unregistered ids (issue 03).
- Any apworld (Python), slot data or version change.


### Implementation (2026-10-22)

> *This was generated by AI.* In the working tree on Ageipelago `0.3.0`, uncommitted. The seven
> code-readable acceptance boxes are ticked; the eighth is the maintainer's in-game playtest.

One file, `Ages.xs`. No apworld, slot data, packet or version change, as the brief required.

- Three module-level bools next to `has_castle` / `has_imperial` — `feudalRegistered`,
  `castleRegistered`, `imperialRegistered` — with `ageRegistered` / `setAgeRegistered` accessors in
  the `ageTechFor` idiom.
- `InitAges` registers an age only when `age <= apMaxAge` *and* its tech is not already
  `cTechStateDone`. The test sits after `ClimbToVanillaAge`, so a done tech means the scenario
  granted the age; registration is read from tech state, never compared against `apVanillaAge`.
- `lockAge(age)` moved inside the same branch. Behaviour-neutral: `lockAge` already no-ops on a done
  tech, and an age above `apMaxAge` is locked by the earlier `capped` loop.
- `ShuffleAgesUpdate` calls `AP_Check_Location(age)` only when `ageRegistered(age)`. `reached++` and
  the `has_castle` / `has_imperial` unlocks stay outside that gate, so the exit condition and the
  unlock order are unchanged.

Two defects found in review and fixed before this was written up:

- **Stale bools across a reinit.** `InitAP` re-runs `InitLocations()` then `InitAges()` when session
  state is lost (`AP.xs:243-249`), rebuilding an *empty* ledger. The bools, being set-only, would
  have survived it and chatted `Location does not exist` every tick. `InitAges` now clears all three
  at the top. This narrows the grilling note "a reloaded save keeps the bools it recorded" — it
  keeps them because `InitAges` re-records them, not because they are never cleared.
- **Unguarded `AddLocation`.** A dropped location (ledger full, or out of `Location` struct
  instances — `ScenarioLocations.xs:46-57`) returned `cInvalidVector` but was still marked
  registered, giving the same chat. `setAgeRegistered` is now behind
  `if (location != cInvalidVector)`. `lockAge` still runs either way, matching today's locking.

**Lint:** all 18 entry points, 0 errors and 6 warnings each (DiscardedFn x5, FirstOprArith in
`TrapItems.xs:68`) — the same baseline recorded in **09**, unchanged by this diff.

**Not done, deliberately:** a review suggested replacing the three bools with a
`FindLocationById(age) != cInvalidVector` scan in the rule. The grilling rules that out — "reads
bools recorded in `InitAges`, one per age [...] No ledger scan per tick". Left as bools.

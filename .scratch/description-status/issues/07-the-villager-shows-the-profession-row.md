# 07: The Villager shows the profession row

**What to build:** Nothing in the game names the villager professions, and a villager whose
profession has not arrived silently refuses the work, so the Villager's own description carries a
row of twelve job icons — job variants are not trainable and have no description of their own,
which is why the row hangs off the Villager. Each job shows its vanilla icon once its profession
item is held and a greyscale icon until then; the greyscale materials already ship in the
Ageipelago UI mod. A job's unit row carries exactly one item, its profession, which both sexes
share, so the row is the twelve items and not the twenty-four locations. Only the jobs this seed
generated appear, which the installed unit table already decides. No text, and no filtering down
to the jobs still locked.

**Blocked by:** 04 (the writer, and the Villager's own status line).

**Status:** done

- [x] The Villager's description carries the row of job icons, with its own status line and the
      vanilla text both intact
- [x] A job reads held when its profession item has arrived, and the two unit rows that share the
      item resolve to one icon
- [x] A job this seed never generated is absent from the row
- [x] An arriving profession item redraws the row in the same pass that refreshes the professions
- [x] Icons are inlined by material name and are not tinted by the line's colour tags
- [x] Without the UI mod installed the greyscale icons render as nothing and everything else still

- [x] The xs lints from the xs folder against the entry point

## Rulings

- 2026-11-13: The row is generated, not tabled. The install writes `ProfessionRow()` into
  `UnitData.xs` beside `LoadUnitTable`, one `professionIcon(itemId, held, missing)` call per job,
  and XS holds no profession icon table, no capacity and no loader.
- 2026-11-13: The vanilla material name is a column on `Age2VillagerJobData`; the greyscale name is
  derived as `ApGrey` plus the job name without spaces, which is how the UI mod already names them.
  No registry module and no lookup that can miss.
- 2026-11-13: No new predicate. The Villager is the tier-zero row of a caveman-exempt line, tested
  inline at the one site that asks, and the redraw rides the loop `RefreshProfessions` already runs
  over professions.

## Comments

> *This was generated by AI during triage.*

- 2026-11-13: Re-aimed from checked to item held on the maintainer's direction. The row now answers
  which jobs a villager can take up rather than which the player has owned, and the checked set
  leaves the ticket entirely. The signal is already in the game: `owned_type_row` installs a job
  row with `items=(place.item.id,)`, one profession item per job, so `hasAllItems` on the row is
  exactly "the item arrived", and `RefreshProfessions` is already called from `GiveItem` for every
  unit item and from `GiveStartupUnits`, which is the redraw hook. The generated set is unchanged —
  `job_possible` gates the items and the locations from the same predicate — but it now reads off
  the installed table rather than the scout reply, so 07 no longer depends on the classification
  channel. The 2026-11-10 pairing ruling retires with it: the two rows per job cannot disagree when
  they hold the same item id, which is also the only job-level key XS has to dedupe on.

- 2026-11-13: Implemented. `Age2VillagerJobData` gains an `icon` column and a derived `grey_icon`;
  `UnitData.profession_row_lines()` generates `string ProfessionRow()` into `UnitData.xs`, one
  `professionIcon` call per distinct profession item in job-table order, or `return ("");` when the
  seed has no jobs. `Unitsanity.xs` adds `professionIcon` and appends `ProfessionRow()` to the
  Villager's description; `RefreshProfessions` redraws it from the loop it already runs.
- 2026-11-13: A first pass was three times this size and was cut back on the maintainer's word. It
  had a `VillagerJobIcons.py` registry with a `JobIcons` dataclass and a drift guard, an
  `addProfessionIcon` loader filling three parallel XS arrays behind a `PROFESSION_ICON_CAPACITY`,
  a `professionLineIds` table with its own capacity and scan to recognise a villager line, an
  `isVillagerBase` predicate that was `isProfession` with one operator flipped, a
  `RefreshVillagerStatusLines` sweep, and a third parameter on `CheckedStatusText`. All of it is
  gone. Generating the row as a function removed the loader, the arrays and the capacity; putting
  the icon on the job removed the registry and the guard; `isProfession` answered the villager
  question; and hanging the banner on the end of the description left `Descriptions.xs` untouched.
- 2026-11-13: The vanilla material names were read out of the game's own `widgetui/materials.json`
  and all twelve resolve there, so the colour half of the row works with no mod installed:
  `UnitIcons00450730`, `IconAction028`, `UnitIcons00650730`, `UnitIcons00350730`, `ResourceWood`,
  `ResourceStone`, `IconAction030`, `BuildingIcons035Farm`, `ResourceGold`, `UnitIcons09650730`,
  `BuildingIcons096Pasture`, `UnitIcons70150730`. The greyscale halves are the twelve `ApGrey*`
  materials the UI mod already ships, each an `ingametechs` atlas entry over the greyscale PNG of
  its vanilla counterpart. Nothing was added to the mod.
- 2026-11-13: The banner goes after the vanilla text rather than between it and the status line,
  which is what keeps `CheckedStatusText` unchanged: `writeUnitStatusLine` appends it. The leading
  newline lives in the generated `ProfessionRow()`, so a seed with no jobs appends an empty string
  rather than a stray blank line.
- 2026-11-13: The banner's owner is the Villager, not the jobs: a job variant is not trainable and
  has no description to hang anything on, which is the ticket's premise. The test is therefore the
  tier-zero row rather than a profession row, and it is written positively — a first pass said
  `isProfession(unit) == false`, which was both redundant against the tier and read as though the
  profession row were being drawn for everything that is not a profession.
- 2026-11-13: Three terms are what it takes. `cavemanExempt` is only ever set on villager-line rows
  and on the owned-type and granted-only rows; `lineId >= 0` drops heroes, escorts and granted-only
  units, which carry `NO_LINE`; and `tier == 0` drops the jobs. What is left is the base Villager.
- 2026-11-13: `hasItem` moved up `Unitsanity.xs` above `writeUnitStatusLine`; XS resolves in file
  order and `professionIcon` reads items.
- 2026-11-13: Unverified in game, as 04, 05 and 06 still are. What a playtest settles: whether
  twelve inlined icons fit the tooltip width without wrapping awkwardly, and whether the greyscale
  art reads as locked at tooltip size rather than as a smudge.

# 09: The client's location channel is a handler

**What to build:** A `LocationHandler` under `client/handlers/`, built like the others, owning
everything the client sends the game about locations. Today the checked-locations channel is the
only file writer still sitting directly on `Age2GameContext`, while buildings, techs, units,
messages, mercenaries, items, campaigns and storage each have a handler. This moves it, and gives
the scouted classification table from ticket 02 a home in the same class as a second channel.

The two channels keep different cadences and different files:

- **Checked locations**, `locations.xsdat`, written every tick from the checked set.
- **Classification**, scouted once at connect, written once, never per tick.

**Blocked by:** None. Ticket 02 builds its classification writer on this.

**Status:** done (classification channel carried by #02)

## What moves

Off `Age2GameContext` in `client/GameClient.py`:

- `sync_checked_locations` (the `locations.xsdat` writer)
- `checked_set_armed`, set in `connect`, cleared in `disconnect` and at the end of `ping_game`
- `confirm_checked_set`, the `CheckedLocationsCount` ack comparison
- the `send_checked_set` term that feeds the Free Locations flag in `ping_game`
- the `locations.xsdat` line in `flush_files`

`ClientStatus.checked_locations` is the AP server's set and stays where it is; the handler reads
it rather than owning it.

The house convention is `*Handler` subclassing `FolderHandler`, constructed in `__init__`, rebuilt
in `disconnect`, and handed its folder in `update_game_user_folder`. `UnitHandler` is the smallest
complete example and the model for the test.

- 2026-11-12: Moved. `LocationHandler` holds the writer, the armed flag and the ack; the ack now
  compares `CheckedLocationsCount` against the count the handler last wrote rather than against
  `ClientStatus.checked_locations`, which is the same number on every path `status_tick` takes and

  the handler the way it calls the unit and tech handlers, and `ping_game` asks it.
- 2026-11-12: The classification writer is left to 02, which owns the scout, the trap derivation and
  the file's layout. 09 ships the class it lives on.
- 2026-11-12: **A flush cannot clear a scout-once file, and this ticket's sixth acceptance line says
  it should.** `flush_files` is not disconnect-only: `status_tick` calls it when it starts following a
  live scenario and again when the game switches scenario. `locations.xsdat` survives that because the
  top of the next tick rewrites it. A classification file written once at connect has nothing to
  rewrite it, so the first scenario switch would strip the colour off every unchecked status line for
  the rest of the session -- the later-scenario case stories 4 and 28 are about. 09 therefore clears
  only its own file and names no classification file at all, so 02 is free to settle the cadence.
  The choices are a flush that leaves the file alone, or a cached scout reply the handler rewrites
  from after each flush. 02's fifth acceptance line ("cleared alongside theirs when the client
  flushes or disconnects") carries the same assumption and is flagged there.
- 2026-11-12: Final names, after the move went in. `arm`/`armed` was not project vocabulary -- it
  entered with 01's own commit `e9ab8bc02` and appears nowhere older, while the three sibling
  client-to-game ping flags name the state and query it (`in_flight`, `is_message_sending`,
  `queue_serial`). `add_locations` was dropped too: it added nothing, and `AddLocations` in
  `ScenarioLocations.xs` already means registering a scenario's id range. The handler now reads
  `send_locations`, `try_sync_checked_locations`, `confirm_checked_locations`,
  `are_locations_sending`, `mark_locations_sent`, `try_flush_from_folder`, over
  `_sending_locations` and `_written_location_count`. `CONTEXT.md` has no entry for any of this;
  a ping-flag term may be worth one.

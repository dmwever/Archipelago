# 08: A checked location's trigger clears itself

**What to build:** Every AP location trigger gains an OR'd `script_call` condition asking whether
the location it checks is already `serverComplete`. A scenario entered or reloaded with that
location already recorded on the server then clears the trigger on its own, instead of asking the
player to do the objective a second time. Trigger enable state is part of an AoE2 save, so a
trigger that had already fired comes back live after a load; this is what makes the reloaded run
agree with the checked set the client is holding.

175 AP triggers across the 18 `AP_*.aoe2scenario` files, less the exclusions below. The work is in
the scenario binaries, read and written through `aoe2kit` and the vendored `AoE2ScenarioParser`.

**Blocked by:** None (can start immediately).

**Status:** ready-for-agent

## The separators are the hard part

Condition ids: `SCRIPT_CALL = 25` (attribute `xs_function`), `OR = 29`, `AND = 57`, all in
`worlds/age2de/AoE2ScenarioParser/datasets/conditions.py`.

Precedence is **`AND` > `OR` > no separator**. Conditions written with no separator between them
are AND'd, but that implicit AND binds *loosest* of the three. `A B OR C D` evaluates as
`A and (B or C) and D`; `A AND B OR C D` evaluates as `((A and B) or C) and D`.

So appending `OR <script_call>` to a trigger whose conditions carry no separators does **not**
give `(A and B and C) or X`. It gives `A and B and (C or X)` — the objective still has to be done,
minus its last condition. That is the failure this ticket exists to avoid.

The rule:

- A trigger with exactly **one** real condition may have `OR` + `script_call` appended directly.
- A trigger with **two or more** real conditions must first have an explicit `AND` separator
  inserted between every adjacent pair, and only then `OR` + `script_call` appended.
- A trigger that already carries an `OR` needs the same treatment around each OR'd group, so that
  the appended `OR` sits at the top level and not inside someone else's grouping.

Measured over the 18 files: 141 of the 175 triggers have exactly one condition, 34 have two or
more (the largest has 13, counting separators). Four already carry an `OR` separator — one each in
`AP_Attila_1`, `AP_Attila_4`, `AP_Joan_2`, `AP_Joan_5` — and **none** carries an `AND`. None loops.

Verify each rewrite by reading the file back with the kit and checking the condition order and
types, not by trusting the write.

## Exclusions

**Every scenario's `AP Victory` trigger.** `Victory()` is the only location wrapper that does more
than check a location — it calls `GiveVictory()`, which sets `completed = 1`, announces and writes
the packet. OR-ing it away would win a reloaded scenario the moment the checked set lands.
`AP_Genghis_6`'s `Victory()` checks two locations and is excluded on the same grounds. Every other
wrapper in every `AP_*.xs` is a bare `AP_Check_Location(id)` and is safe.

## The XS side

`IsServerLocationComplete` goes through `GetLocationById`, which chats `Location Not Found` on a
miss. A condition evaluated every tick on every AP trigger in the scenario must never chat, so add
a silent predicate that returns `false` for an id the ledger does not hold, and have the triggers
call that.

The OR branch cannot double-send: it reaches `AP_Check_Location`, which sets `scenarioComplete`,
and `FilterCompletedNotSent` only queues a location that is `scenarioComplete` **and not**
`serverComplete`.

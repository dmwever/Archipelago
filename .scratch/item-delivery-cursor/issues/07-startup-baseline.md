# 07: Retire `startup.xsdat`, so starting resources land once

**What to build:** `StartingResources` and `TCResources` are paid out by `startup.xsdat` at every
`ConnectAP` *and* streamed through the item window, so every scenario start pays them twice. They
cannot be governed by the once-ever mark from ticket 02 — they are per-scenario-start, and they
still have to land immediately when received mid-scenario.

The window already does exactly that on its own: the cursor starts at 0 in every new scenario, so
it replays the whole stream there, and a loaded save carries its own cursor. Delete the second path:
`startup.xsdat`, `GiveStartupItems`, and the client's `sync_starting_resources`.

Spec: `worlds/age2de/docs/spec-item-delivery-cursor.md` (Retire `startup.xsdat`, so starting resources have one path).

## Amendment

(2026-10-22) The `startupBaseline` design below was built first and works, but it only coordinates
two payment paths where the window alone is enough, and it needed a not-yet-read `-1` state to
close a race against the packets `WriteAP` sends before `ConnectAP` reads the pile. Retiring the
file removes both. The cost is latency: starting resources now arrive through the window at
`ITEM_WINDOW` entries per `ReadItems` pass instead of all at once at `ConnectAP`. The Triage below
is kept for history; its "Where the code goes" no longer applies.

## Triage

> *This was generated by AI during triage.*

**Category:** bug. **State:** ready-for-agent.

**The rule.** A starting resource (`StartingResources` or `TCResources`; both are treated alike)
pays out once per scenario run, through exactly one path:

- If it was in the `startup.xsdat` that this scenario's `ConnectAP` read, the startup pile pays it
  and the item window must not pay it as well.
- If it arrived after that read (mid-scenario), the window pays it immediately.
- The next scenario's startup pile pays the whole pile again. These are starting items, so this is
  not a once-ever grant: do **not** add them to `ONE_SHOT_ITEMS` or the spent mark.

`startupBaseline` encodes exactly that. The design above stands.

**Worse than described.** The game's `appliedItemCount` starts at 0 in every scenario
(`AP.xs:22`), so the window replays the whole stream on each scenario start. Today every starting
resource pays twice at **every** scenario start, not only the first one after it is received in the
menu.

**Where the code goes.** Starting resources were deliberately kept out of `ItemHandler`.

- Writing `startup.xsdat`, including the new leading `startupBase`, stays in
  `Age2GameContext.sync_starting_resources` (`client/GameClient.py:336`). So does the file's
  removal in `flush_files`. Do not move either into `ItemHandler`. (06's amendment lists
  `sync_starting_resources` as moved; it was not.)
- `ItemHandler` only consumes the baseline. It is passed in from the packet next to
  `applied_item_count`, and `_id_for_game` returns `Items.SKIP_ITEM_ID` for a starting resource whose
  index is below it.
- Packet: the game writes `startupBaseline` in place of one reserved int after `appliedItemCount`
  (`AP.xs`, loop 26 → 25). The client reads it after `applied_item_count` and skips 25
  (`GameClient.py:113`). Nothing before byte 72 moves.
- `startupBase` = `len(unlocked_items)` at the moment the file is written. Header and contents are
  written together, so the baseline always matches the pile the game read.
